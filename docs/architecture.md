## 一、这份文档回答什么

选型阶段真正需要判断的，不是功能清单有多长，而是四个问题：

1. 这套东西的**内核**是不是真的存在，还是把一堆页面拼在一起
2. 换一个行业，是**扩展**还是**重做**
3. 交付到客户现场，**装得起来、跑得下去、升得动**吗
4. 卖源码这件事，**法律上干净**吗

本文按这个顺序展开。

## 二、设计约束

架构不是自由选择的结果，是被约束逼出来的。四条约束先摆清楚：

| 约束 | 含义 | 后果 |
| --- | --- | --- |
| **交付要轻** | 客户和集成商都要能自己装、自己运维 | 排除一切需要专职运维的形态 |
| **源码要能卖** | 客户会拿到代码并修改 | 许可证必须干净，扩展点必须明确 |
| **法规会变** | 每年都有新规、新口径、新报表 | 知识与逻辑必须解耦 |
| **现场会断网** | 车间、地下室、内网隔离是常态 | 云端不能成为单点 |

这四条加起来，直接决定了后面所有取舍。

## 三、架构原则

**原则一：内核稳定，行业可变**

稳定的是"证据如何产生、如何保存、如何证明"；可变的是"这个行业有哪些义务、怎么检查、报什么表"。
两者混在一起的系统，第二个行业就会开始崩。

**原则二：配置优先，代码兜底**

能通过配置表达的，绝不写代码。确实表达不了的，限制在一个受控的扩展边界内。
这条守不住，交付成本会随客户数量线性上升。

**原则三：现场优先，云端增强**

凡是涉及安全与联锁的判定，必须在现场侧成立。网络只负责同步，不负责正确性。

**原则四：只追加，可校验**

履职记录一旦产生，就进入只追加通道。修正通过"新增一条说明"完成，而不是"改掉原来那条"。
这是"合规"与"记录"的分水岭。

**原则五：边界清晰，责任可分**

哪个模块属于内核、哪个属于行业、哪个属于客户定制，必须在工程结构上看得见，而不是靠文档约定。

**原则六：可交付性优先于技术先进性**

一个装不起来的新架构，价值为零。技术选择的默认答案是"成熟、可接手、人才好招"。

## 四、分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 体验层    管理端 │ 移动端 │ 监管视图 │ 开放接口                 │
├──────────────────────────────────────────────────────────────┤
│ 行业层    行业知识与模板：检查口径、报表、术语、权限码          │
│           （可裁剪、可扩展、可替换，不含通用业务逻辑）           │
├──────────────────────────────────────────────────────────────┤
│ 内核层    合规证据链                                            │
│           对象 · 义务 · 日历 · 取证 · 台账 · 闭环 · 报送 · 责任   │
├──────────────────────────────────────────────────────────────┤
│ 平台层    组织 · 权限 · 流程 · 文件 · 审计 · 授权                │
├──────────────────────────────────────────────────────────────┤
│ 集成层    监管平台对接 · 设备接入 · 第三方服务                   │
├──────────────────────────────────────────────────────────────┤
│ 数据层    关系数据 · 缓存 · 对象存储                             │
└──────────────────────────────────────────────────────────────┘
        ▲                                        ▲
        │                                        │
   边缘节点（现场自治 / 断网续传）          上级监管平台 / 行业平台
```

各层的职责边界：

| 层 | 有 | 没有 |
| --- | --- | --- |
| 体验层 | 交互、视图、导出 | 业务规则 |
| 行业层 | 行业知识、模板、报表 | 通用流程 |
| 内核层 | 证据链的全部规则 | 任何行业词汇 |
| 平台层 | 通用能力 | 业务语义 |
| 集成层 | 适配与转换 | 业务判断 |

**"内核不含任何行业词汇"是一条硬线。** 一旦内核里出现"电梯""气瓶"这类词，扩展性就开始漏气。

## 五、证据链内核

### 5.1 八个能力域

| 能力域 | 职责 |
| --- | --- |
| **合规对象** | 统一表达单位、场所、设备、装置及其层级关系与属性 |
| **义务与标准** | 将法规条款转译为可执行义务，带版本与生效期 |
| **合规日历** | 由义务推导周期任务，按岗派发，逾期升级 |
| **现场取证** | 采集具备可采信性的第一手证据 |
| **可信台账** | 只追加的履职记录，具备自证能力 |
| **隐患闭环** | 发现、整改、复查、销号的全过程追踪 |
| **报送与档案** | 对外报送、对内归档，两者共用同一份证据 |
| **责任矩阵** | 岗位职责的映射、兼岗校验与生效期管理 |

这八个域之间的关系是**单向依赖**：对象支撑义务，义务产生任务，任务产生证据，证据进入台账。反向依赖一律不允许。

### 5.2 三个关键设计

**版本化：让历史可以被还原**

法规每年变，检查口径也会变。如果只保留"当前版本"，那么翻旧账时无法回答"当时依据什么"。

所以系统中的义务、检查口径、报表模板都具备版本与生效期，且**任务在生成时即绑定当时的版本**。之后无论模板怎么改，这条记录都能按当时的依据完整复现。

这一条是普通巡检工具做不到、也不愿意做的地方——它没有技术难度，难的是想清楚"为什么必须这样做"。

**链式校验：让修改无处可藏**

记录进入台账后，前后逐条勾连。修改任意一条，后续校验即不成立。

配套的是**每日锚点**：把当天的校验状态固化到与业务数据物理分离的位置。这样即使有人能改业务库，也无法同时抹掉锚点。

这条链路的目的不是"绝对不可改"，而是**任何修改都会留下痕迹、且能被独立验证**。这是软件能做到的诚实边界。

**双时间与可复现导出**

现场设备的时钟不可信。因此每一次取证同时记录设备时间与服务端接收时间，并计算时差；判定以服务端为准。

导出档案时，把依据版本、校验信息与锚点标识一并写入，使纸质档案同样可验。监管拿到的不只是一叠纸，而是一份可以被核对的材料。

### 5.3 为什么不上完整流程引擎

审批与周期任务是两类问题，用同一套机制解决会付出不必要的复杂度：

- **周期任务、逾期升级、简单闭环**：状态机足够，规则可配置
- **多级会签、加签、动态审批链**：才需要流程引擎

把流程引擎用在第一类场景，是很多项目"配不动、改不敢改"的根源。

## 六、行业扩展模型

扩展能力是这套架构的**唯一验收标准**：

> 新增一个行业方向，是否需要修改内核？

答案必须是"不需要"。为此设置了四层边界：

```
第一层  配置层       周期规则、检查项、字段、字典、角色、审批链、报表映射
第二层  模板层       行业检查口径、报表模板、菜单与权限、初始化数据
第三层  扩展层       该行业的特殊规则与特殊对接（受控规模）
第四层  内核层       禁止任何形式的行业定制
```

第四层是红线。这条线守不住，产品就会退化成若干个项目的集合——表面上还在卖"产品"，实际上每个客户都是定制开发。

工程上还有两条配套约束：

- 内核、行业、客户定制在**工程结构上物理分离**，不靠文档约定
- 交付物可复现：给定内核版本、行业版本与定制内容，必须能构建出完全一致的交付包

## 七、集成与现场

### 7.1 平台对接

上级监管平台的接口开放程度不由我们决定，因此对接被设计成三层可配置能力：

| 层 | 内容 | 谁来配 |
| --- | --- | --- |
| 字段映射 | 源字段到目标字段的转换 | 实施人员，界面可配 |
| 报文模板 | 报文结构与格式 | 实施人员，无需发版 |
| 协议驱动 | 同步、批量、文件交换、人工导入 | 开发人员 |

配套两项能力：**报文留痕与重放**（出了问题能查、能重推）、**对接自检**（交付前先自查字段是否对齐）。

保留"辅助填报"作为兜底：生成符合平台格式的文件，由客户自行上传。这不是妥协，而是对现实的尊重——大量项目拿不到接口文档，把交付押在接口上是赌博。

### 7.2 现场与边缘

工业现场的设备类型繁杂，且往往不在 IT 部门的管辖范围内。因此现场侧采用独立的边缘节点：

- **采集**：串口、工业总线、工业以太网、物联网协议等主流方式
- **执行**：打印、联锁、指令下发
- **自治**：断网期间本地留存，恢复后按序回传，不重不漏
- **管理**：远程配置与升级，可按需关闭

关键约束是**联锁判定在现场完成**。"不扫码不开阀"这类逻辑，必须断网也生效。

## 八、部署形态

| 形态 | 适用 | 交付方式 |
| --- | --- | --- |
| 单机版 | 单一企业、小集成商 | 一台服务器，全离线安装包 |
| 私有化版 | 集团、园区 | 离线镜像 + 增量升级 |
| 政务云 / 等保三级 | 政府、园区 | 双机或容器化 + 国密 + 审计，配套测评材料 |
| SaaS 多租户 | 小微企业 | 共享基础设施，租户隔离，我们运维 |
| 边缘版 | 工厂现场 | 独立节点，单独授权 |

三种数据组织方式（共享、独立、混合）由**配置切换，代码路径不变**。不出现"某版本分支"这种会长期反噬的设计。

## 九、非功能与合规

| 项 | 要求 | 我们的做法 |
| --- | --- | --- |
| 等保 2.0 三级 | 园区、政府强制 | 身份鉴别、访问控制、安全审计、入侵防范、数据完整性、备份恢复、个人信息保护逐条对表，材料随包 |
| 商用密码应用 | 政务与关基项目常要求 | 国密传输、存储加密、签名验签，按项目切换 |
| 国产化适配 | 政府项目常态 | 国产操作系统、数据库、芯片平台，代码层面规避数据库特有语法 |
| 性能 | 园区口径：并发数百、在线上千 | 单机满足；瓶颈在媒体上传与报表生成，用异步化处理 |
| 视频 | 存储 30 天以上，报警留存 1 年 | 不自建流媒体，对接主流平台 |
| 备份 | 每日全量 + 增量 | 校验脚本可交付，满足测评取证需要 |

需要说明的一点：**软件不能单独决定测评结果**。等保与密评取决于机房、网络、管理制度与运维流程的整体条件，我们能做的是把软件侧的材料与配置准备到位，并配合整改。

## 十、交付、升级与授权

**离线交付**：安装包自带运行时、字体、文档转换组件与全部依赖。客户没有外网，也能完成安装、运行与导出。

**增量升级**：数据库变更、前端资源、配置迁移三部分打包，带回滚路径。目标是一小时内完成一次升级。

**授权体系**：按模块、租户数、设备数分档签发，机器绑定，支持离线激活。

**诊断能力**：一键导出环境信息、日志与配置（脱敏后），把远程支持的成本降一半。

## 十一、演进路线

按"先能交付，再能复制"排序，而不是按技术难度排序。

| 阶段 | 目标 | 验收 |
| --- | --- | --- |
| 内核成型 | 证据链八个域打通，从任务到档案的链路完整 | 一个行业方向能跑完全流程并导出可核验档案 |
| 首个行业落地 | 行业口径、责任矩阵、隐患闭环完整 | 一个真实使用单位能用、能经得起一次检查 |
| 行业复制 | 验证扩展模型是否成立 | 新增行业只做知识与模板，内核不变 |
| 商业化 | 离线包、授权、行业货架、伙伴交付能力 | 集成商可独立完成一次部署 |

**第三阶段是真正的分水岭。** 如果新增行业仍然需要改内核，说明前面的设计没有兑现，后面的规模化也不成立。

## 十二、架构治理

架构不会自动保持形状。我们每季度做一次审计，只看六件事：

- 新增行业方向，内核是否零改动
- 客户特殊需求，是否绝大多数落在配置层
- 历史记录是否都能按当时依据复现
- 断网恢复后，数据是否零丢失、零重复
- 关闭全部外网，系统是否仍可完整运行
- 交付包内是否出现许可证不合规的组件

任何一条不成立，就停下来修，而不是往下加功能。

## 十三、常见技术疑问

**为什么是单体，而不是微服务？**

因为交付对象决定形态。客户现场通常是一到两台服务器，运维由客户或本地集成商承担。微服务带来的注册、网关、链路、分布式事务，在这类场景里是纯成本。

真正需要独立的只有现场边缘节点——它部署位置不同、升级节奏不同、协议各异。

**换一个技术框架成本高吗？**

内核部分不依赖具体框架，领域规则与框架注解是分离的。所以更换外壳的代价可控。这也是当初刻意保留的一条退路。

**为什么不用低代码平台做底座？**

低代码解决的是"快速生成界面"，而这里真正难的是"证据如何成立"。前者能省两周，后者决定产品能不能卖。况且低代码平台的生成物在源码授权场景下往往带来额外的授权与可控性问题。

**能不能只交付部分模块？**

可以。交付包按需组装，客户不必为用不到的能力付出部署与运维成本。

**源码交付后，客户改坏了怎么办？**

这是必然会发生的事，所以设计上做了两件事：一是把"不建议改"的区域在结构上隔离并标注清楚；二是让定制部分与内核分离，升级时不需要合并定制代码。剩下的靠交付文档与培训解决。
