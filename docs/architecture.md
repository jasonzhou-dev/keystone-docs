# 磐基 Keystone · 技术架构说明

> 本文是面向技术选型与尽调的架构说明，可直接内部传阅。
> 产品定位见 [README](../README.md)，常见问题见 [faq.md](./faq.md)。

---

## 一句话

> **模块化单体（Spring Boot 3 + Vue 3）+ 一个「合规证据链」内核 + 可裁剪的行业包 + 独立的边缘采集网关 + 适配器式报送对接。**

判断这套架构成不成立，标准只有一条：

> **能不能让第 11 个行业包只写模板、不写 Java？**

---

## 一、决定架构的六个事实

| 事实 | 对架构的约束 |
| --- | --- |
| 大多数法规强制场景的内核完全相同（日历 / 模板 / 取证 / 台账 / 闭环 / 报送 / 责任矩阵） | 必须抽内核，行业只做配置，否则做到第五个方向就维护不动 |
| 交付由小团队完成，客户与集成商都要自己部署 | 单体 + 一键离线安装包；微服务、容器编排、服务网格全部否决 |
| 源码会被客户修改 | 依赖许可证必须干净；必须有三层扩展点；禁止改内核 |
| 法规每年变，检查要"翻旧账" | 一切模板 / 义务 / 报表版本化 + 生效期，历史记录按当时版本复现 |
| 无纸化维保、危废五即、日管控的核心是"证明没改过" | 取证 → 哈希链 → 存证锚，这是护城河，不是附加功能 |
| 上级平台接口不公开、现场硬件协议不统一 | 对接做成可插拔适配器 + 辅助填报兜底，不能阻塞交付 |

## 三、五个关键技术决策

### 决策 1：模块化单体，不是微服务

| 方案 | 判断 |
| --- | --- |
| 微服务 + 注册中心 + 网关 | ✗ 集成商装不起来；小团队运维不动；低客单客户养不起 |
| 单体大泥球 | ✗ 卖不出行业包，改一处动全身 |
| **多模块单体 + 按包裁剪构建** | ✓ 一个进程能跑，也能按客户只装两个行业包 |

落地：按行业包组合打包出交付物；前端按包动态注册路由与菜单。

**唯一拆分出去的进程是边缘采集网关**——它部署在现场、独立升级、协议插件按需下发。

### 决策 2：Spring Boot 3 + Vue 3

选底座的六条硬标准，以及为什么这三样是产品化的前提：

| 标准 | 不满足的后果 |
| --- | --- |
| 许可证允许商用与再分发 | 卖源码即违约 |
| 原生多租户 + 数据权限 | 后期补租户字段是灾难 |
| JDK 17 / Boot 3 | 信创环境跑不了，两年后要重写 |
| 国内认知度高、教程多 | 教学与招人成本翻倍 |
| 可裁剪 | 只装两个包的客户被迫背一身模块 |
| 无强绑定中间件 | 离线部署装不起来 |

**不在标准里的**：功能多不多、界面好不好看、有没有低代码。这三样都会把选型带偏。

> 底座为 MIT 许可的开源项目二次开发，保留版权与许可证声明。这一点在合同和宣传里如实写明，比宣称"完全自研"更专业，也更安全。

### 决策 3：移动端 uni-app

理由都是工程与交付层面的：

- 客户要**微信小程序**，送气工、安全员、家长端都从微信进
- 一套 Vue 语法出小程序 + H5 + App，交付成本最低
- 集成商接手后能自己改

**代价是离线能力弱**（车间、地下室、井道无信号），对策分三档：

| 离线程度 | 方案 |
| --- | --- |
| 轻 | 本地队列 + 失败重传 + 幂等键，覆盖大多数场景 |
| 中 | 挂本地 SQLite 插件，联网后按序上送 |
| 重（整厂内网） | 走原生壳，同一套 Vue 代码 + 本地库，不走小程序 |

### 决策 4：配置驱动 + 三层扩展

```
第 1 层  配置层        周期规则、检查项、字段、字典、角色名、审批链、报表映射
第 2 层  模板包层      检查项 JSON、报表模板、菜单权限码、初始化数据
第 3 层  接口实现层    检查规则 / 报表渲染 / 平台适配 / 设备驱动 / 导出器（≤500 行）
第 4 层  改内核        禁止
```

工程保障（不做这些，两年后必然崩）：

- 内核、行业包、客户定制三层目录分离
- 持续集成检查客户目录不得修改内核内部类，只能实现接口
- 每个客户交付物 = 内核版本 + 行业包版本 + 定制层提交 → 可复现构建

### 决策 5：一个库多租户，大客户独立库

| 部署 | 数据隔离 |
| --- | --- |
| SaaS | 共享库 + 租户字段 + 租户插件 + 数据权限（部门 / 场所） |
| 大客户私有化 | 独立库（单租户，租户字段固定值，代码路径不变） |
| 政务云 | 独立库 + 等保三级 + 国密 |
| 集团多厂区 | 独立库 + 多组织 + 场所维度隔离 |

关键：**同一套代码靠配置切三种模式**，不出现"SaaS 版分支""私有化版分支"。

## 四、内核：合规证据链

### 4.1 八张核心表

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `ce_object` | 合规对象（单位 / 场所 / 设备 / 管线 / 车辆 / 罐） | `object_type`, `code`, `parent_id`, `attrs`(JSON) |
| `ce_obligation` | 义务库（法条 → 义务） | `source_doc`, `clause`, `frequency`, `evidence_rule`, **`version`, `effective_from`** |
| `ce_checklist_tpl` | 检查项模板 | `pack_code`, `object_type`, `items`(JSON), `version` |
| `ce_plan` | 周期计划（RRULE） | `obligation_id`, `rrule`, `assignee_rule` |
| `ce_task` | 任务实例 | `plan_id`, `due_at`, `assignee_id`, **`tpl_version_id`**（固化版本） |
| `ce_evidence` | 取证 | `task_id`, `type`, `file_key`, `sha256`, `gps`, `device_time`, `server_time`, `sign` |
| `ce_ledger` | 台账（只追加） | `prev_hash`, `hash`, `payload`, `anchor_id` |
| `ce_finding` / `ce_rectify` | 隐患 / 整改闭环 | `level`, `deadline`, `escalate_at`, `verify_by` |

再加两张支撑表：

- `ce_role_matrix` — 责任矩阵（主要负责人 / 安全总监 / 安全员 / 岗位，带生效期与一人多职校验）
- `ce_submission` — 报送批次 + 回执 + 报文摘要

### 4.2 为什么必须"版本化 + 生效期"

监管翻旧账时问的是：**某年某月那次日管控，你对照的是哪一版清单？**

所以 `ce_task` 必须固化 `tpl_version_id`，渲染与导出都用当时版本。

这是普通巡检 App 做不到、也不愿意做的地方，也是"合规"与"打卡"的分界线。

### 4.3 不可篡改：三层，别过度设计

```
第 1 层  只追加表（应用侧无 UPDATE / DELETE 权限）+ 数据库审计
第 2 层  哈希链：hash_i = SM3( prev_hash ‖ canonical_json(payload) ‖ server_time )
         canonical_json = 键排序 + 定点小数 + UTF-8，避免序列化差异
第 3 层  存证锚：每日把 chain_head 写入独立锚表（另一库 / 另一账号），
         可选对接时间戳服务或司法链（大客户选配，不做成必选）
```

三个工程细节，决定这套东西能不能被监管认可：

1. **双时间**：设备时钟与服务端接收时间都存，并计算时差；判定以服务端为准
2. **原图存证**：照片 / 视频存对象存储，SHA-256 入库，导出时附校验工具，监管可自行验证未被替换
3. **可复现导出**：导出 PDF 时把"模板版本 + 记录哈希 + 锚点编号"打进页脚，形成闭环证据

国密：SM2 / SM3 / SM4 通过可切换的加密提供者实现，默认国际算法，等保 / 密评客户切国密。

### 4.4 合规日历：不上完整工作流引擎

| 需求 | 方案 |
| --- | --- |
| 日 / 周 / 月 / 季 / 年周期、跳过节假日、按对象类别差异 | RRULE（iCalendar 规则）+ 自研调度，不引集群调度器 |
| 任务派单、超期提醒、升级到上级 | 状态机 + 升级规则表 |
| 特殊作业票（动火 / 受限空间等八大票）多级审批、会签、加签 | 嵌入式流程引擎，**只在这个场景用** |
| 简单整改闭环（发现 → 整改 → 复查 → 销号） | 自研状态机，不用流程引擎（配置成本高于收益） |

判断口径：**审批节点固定且少 → 状态机；审批链由客户配置且要会签 → 流程引擎。**

### 4.5 报送与导出

- 报表：Word 模板渲染 + Excel，政府要的九成是 Word / Excel，不是花哨 PDF
- PDF：需要时用 LibreOffice 无头转换（私有化部署自带），不引入商业授权库
- 报送：**outbox 模式** —— 先落库、定时推送、失败重推、回执入库、报文原文存对象存储
- 兜底：**辅助填报**（生成符合平台格式的文件让企业自己上传）。这是现实选择：大量客户拿不到接口文档，不能把交付押在接口上

## 五、集成层：把"平台对接"做成可复用能力

对接是这类项目最大的隐形门槛，架构上必须让它不侵入内核。

```
interface PlatformAdapter {
    code()                                    // 平台标识
    push(batch) -> PushResult                 // 推送
    query(batchNo) -> Receipt                 // 查回执
    defaultMapping() -> List<FieldMapping>    // 默认字段映射
}
```

三层配置化，让本地集成商能自己接大部分活：

1. **字段映射表**（界面可配）：源字段 → 目标字段 → 转换函数（字典 / 日期格式 / 单位换算 / 拼接）
2. **报文模板**：JSON / XML / WebService / 表单 POST，模板存库可改，不用发版
3. **协议驱动**：HTTP 同步、定时批量、文件交换（SFTP / 共享目录）、人工导入

再加两件真正有用的能力：**报文留痕与重放**、**对接自检工具**（给一张表，客户自己验证字段对不对）。

## 六、边缘采集网关

现场一定会遇到：电子秤串口、标签打印机、PLC、数采仪、摄像头、门禁、充装秤。这些不能塞进主应用。

```
keystone-edge（独立进程，4C2G 可跑）
├─ 采集：串口 / TCP / Modbus TCP-RTU / OPC UA / MQTT / HJ 212 / JT-T 808
├─ 执行：标签打印（ZPL / TSPL / CPCL / ESC-POS）、开阀联锁（继电器 / PLC 写点）
├─ 缓存：本地 SQLite，断网存数日，恢复后按序补传（幂等键）
└─ 管理：远程配置下发、版本升级、日志回传（可关闭）
```

三个约束：

1. **协议插件按需加载、独立分发**：避免把商业 SDK 混进主源码包
2. **联锁逻辑放在网关上，不下发到云**：例如"不扫码不开阀"必须断网也能生效
3. **网关是独立部署项**：现场调试成本高，单独评估

## 七、部署形态矩阵

| 形态 | 适用 | 组件 | 交付方式 |
| --- | --- | --- | --- |
| **A 单机版** | 单一企业、小集成商 | 数据库 + 缓存 + 应用 + 本地文件存储 + 反向代理 | 容器编排 / Windows 一键离线包（4C8G） |
| **B 私有化版** | 集团、园区 | 同上 + 对象存储 + 备份 | 离线镜像 + 升级包 |
| **C 政务云 / 等保三级** | 政府 | 双机或容器 + 国密 + 审计 + 堡垒机 | 测评配合包（拓扑、配置基线、密评材料） |
| **D SaaS 多租户** | 小微企业 | 共享库 + 租户插件 | 我们运维，按年订阅 |
| **E 边缘版** | 工厂现场 | 边缘网关 | 单独安装、单独授权 |

工程要求，都直接影响能不能规模化交付：

- **离线安装包**：不能假设客户有外网。依赖、字体、文档转换组件、运行时全打进去
- **升级包**：版本化 SQL + 前端资源 + 回滚脚本，一小时内能升级完
- **授权模块**：机器码 + 签名许可证，按模块 / 租户数 / 设备数分档
- **诊断包**：一键导出环境 + 日志 + 配置（脱敏），远程支持成本降一半

## 八、技术选型与许可证

| 层 | 选型 | 许可证 | 备注 |
| --- | --- | --- | --- |
| 后端 | JDK 17 + Spring Boot 3.x | Apache 2.0 | 信创环境需验证（麒麟 / 统信） |
| 底座 | 若依 Vue-Plus 系 | MIT | 多租户、权限、ORM 现成 |
| ORM | MyBatis-Plus | Apache 2.0 | 避免存储过程，兼容达梦 / Kingbase |
| 权限 | Sa-Token | Apache 2.0 | 上手与二次开发成本低 |
| 工作流 | 嵌入式流程引擎（仅作业票） | Apache 2.0 | 不引入全家桶 |
| 前端 | Vue 3 + Vite + Element Plus + Pinia | MIT | 集成商最熟 |
| 移动端 | uni-app（Vue 3）+ 本地 SQLite | Apache 2.0 | 出小程序 / H5 / App |
| 报表 | poi-tl + POI | Apache 2.0 | Word / Excel 模板 |
| 建库迁移 | Flyway | Apache 2.0 | 升级包的基础 |
| 缓存 | Redis | BSD | 单机即可 |
| 消息 | 先 outbox 表；量大再上消息队列 | MPL 2.0 | 小部署不上 Kafka |
| 对象存储 | 抽象层 + 本地磁盘 / 兼容 S3 | — | **注意：部分对象存储为 AGPLv3，卖源码禁用** |
| 时序（可选） | 时序扩展或分区表 | Apache 2.0 / 类 BSD | 部分国产时序库为 AGPL，慎用 |
| 调度 | 框架自带调度 + 数据库锁 | — | **部分分布式调度为 GPLv3，别打进源码包** |
| 加解密 | BouncyCastle + 国密 GM | MIT | 做可切换接口 |

> **红线**：任何 AGPL / GPL 组件不得进入交付源码包。对象存储、时序库、分布式调度这三类最容易误踩。

## 十、AI 放在哪，以及不要放在哪

| 用 | 怎么用 | 价值 |
| --- | --- | --- |
| ✓ 法规 → 检查项草稿 | 解析部令 / 规范，生成检查项初稿，人工校对 | 直接降交付成本，收益最高 |
| ✓ 证照 / 报告 OCR | 营业执照、检验报告、磅单、健康证识别入档 | 少录一遍，客户感知强 |
| ✓ 报告文本生成 | 周排查报告、会议纪要、执行报告摘要 | 省客户人力 |
| ✓ 图片初筛 | 未戴安全帽、异物（只做提示，不做判定） | 选配 |
| ✗ 自研视频算法 | — | 硬件厂商战场，不做 |
| ✗ "AI 大屏 / 智能体"当卖点 | — | 客户不为它付钱，反而拖慢交付 |

架构上：AI 一律走**旁路服务**，主应用只调接口，失败必须降级为人工。**核心链路不允许依赖 AI。**

## 十一、非功能要求

| 项 | 要求 | 落地 |
| --- | --- | --- |
| 等保 2.0 三级 | 园区 / 政府强制 | 七项逐条对表：身份鉴别、访问控制、安全审计、入侵防范、数据完整性、备份恢复、个人信息保护 |
| 商用密码应用 | 政务 / 关基项目常要求 | 国密传输 + 存储加密 + 签名验签，接口可切换 |
| 信创 | 政府项目常态 | 麒麟 / 统信 + 达梦 / Kingbase + 鲲鹏 / 飞腾，禁用数据库特有语法与存储过程 |
| 性能 | 并发 ≥300、在线 ≥1000、静态 ≤2s | 单机足够；瓶颈在图片上传与报表生成，用异步队列 |
| 视频 | 存储 ≥30 天，报警视频 ≥1 年 | 不自建流媒体，接海康 / 大华 / GB28181 |
| 备份 | 每日全量 + 增量 | 备份校验脚本可交付（等保要材料） |

---

## 十二、明确不做的事

1. **不做微服务**：交付成本 ×3，收益为 0
2. **不自研通用低代码平台**：只做"模板 + 表单渲染"这一窄条
3. **不为每个客户 fork 代码**：一旦 fork，第二十个客户就崩了
4. **不碰硬件主业**：做适配不做产品
5. **不混入 AGPL / GPL 组件**：卖源码时这是法律风险，不是技术偏好
6. **不做"又一个巡检 App"**：没有责任矩阵、没有版本化模板、没有哈希台账，就只是打卡工具

## 十三、落地路线

| 阶段 | 交付 | 验收标准 |
| --- | --- | --- |
| **P0 内核** | 八张表 + 模板引擎 + 日历派单 + 移动取证 + 哈希台账 + Word/Excel 导出 + 多租户 + 授权 | 一个行业包的检查项跑通"日管控 → 导出 PDF"全链路 |
| **P1 特种设备包** | 八类对象模板 + 责任矩阵 + 隐患闭环 + 履职档案 | 一个真实使用单位能用、能过检查 |
| **P2 电梯 / 气瓶包** | 维保工单、上级平台对接位、充装联锁（含边缘网关） | 一家维保公司 + 一个充装站上线 |
| **P3 环保包** | 排污证结构化 + 执行报告生成 + 危废五即 + 适配器 | 一家重点排污单位 + 一家环保管家白标 |
| **P4 商业化** | 行业包货架、离线安装包、课程 / 社群素材、源码授权分档 | 集成商能独立部署一个包 |

后续行业包只写模板与报表——**这是架构是否成功的唯一检验**。

## 十四、架构自检清单

每季度对一次，任何一条为"否"都要停下来修：

- [ ] 新增一个行业包，改动内核代码行数是否为 0？
- [ ] 客户特殊需求，是否有 ≥80% 落在配置层？
- [ ] 所有任务实例是否固化了模板版本？历史导出能否复现？
- [ ] 断网 24 小时后恢复，取证数据是否零丢失、零重复？
- [ ] 关掉全部外网，系统是否仍能完整跑（含查询、导出、打印）？
- [ ] 交付源码包里是否出现 AGPL / GPL 依赖？
- [ ] 一套代码能否在 MySQL / 达梦 / Kingbase 上各跑一遍？
- [ ] 从零安装到可用，单机版是否 ≤ 1 小时？

## 附：为什么不用 Solon

社区常问"为什么不上国产框架"。结论是：**主平台不用，边缘网关可优先考虑。**

| 场景 | 用不用 | 理由 |
| --- | --- | --- |
| 主平台（多租户 + 私有化 + 卖源码） | ✗ | 现有资产复用归零；受众与生态双双缩水；深度绑定 Spring 的组件没有等价物 |
| 边缘采集网关 | ✓ 优先候选 | 工控机 4C2G、启动快、内存小、不依赖生态 |

内核层坚持框架无关：领域模型用纯对象 + 接口，框架注解只出现在 adapter / controller / config 层。这样将来换框架只改外壳，内核与行业模板不动。
