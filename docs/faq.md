## 定位

### 1. 磐基是什么？

面向**法规强制型场景**的合规留痕中台。

它做三件事：把法规条款转译成可执行的周期义务；用任务与现场取证把履行过程固化成证据；用可信台账与履职档案证明"做过、谁做的、没被改过"。

适用领域：特种设备、电梯维保、气瓶充装、排污许可与危废、食品主体责任、消防、职业健康等——共同点是**有明确法规义务、检查时会被要求拿出材料**。

### 2. 和巡检 App / 打卡工具有什么区别？

| 监管会问 | 打卡工具 | 磐基 |
| --- | --- | --- |
| 对照的是哪一版清单？ | 只有当前版本 | 记录与当时依据绑定，可复现 |
| 记录事后改过吗？ | 数据库可直接改 | 只追加 + 链式校验 + 独立锚点 |
| 谁负责、谁漏了？ | 没有责任主体 | 责任矩阵，到岗到人 |

概括：**打卡工具证明"有人去过"，合规系统证明"履职了"。** 这个差别在平时看不出来，在检查与追责时是决定性的。

### 3. 能不能只上一个行业方向？

可以。行业能力按需启用，交付包只包含你实际使用的内容，不为用不到的功能付部署与运维成本。

### 4. 一套系统能不能同时管特种设备、环保、食品？

能，而且这正是它存在的理由之一。这几个领域的内核是同一个——对象、义务、证据、台账、闭环、责任；差别在知识与模板。

多领域共用一个底座的实际价值是：一个安全或合规部门能在一套系统里看到全部履职情况，而不是维护三套账号体系、三份台账、三次培训。

### 5. 和低代码平台做出来的系统有什么不同？

低代码解决的是"快速生成界面"，这里真正难的是"证据如何成立"。

用低代码能很快做出"填报页面"，但版本可溯、链式校验、责任矩阵、离线自治这些能力，恰恰是低代码平台最不擅长的部分——它们不是界面问题。

另外在源码授权场景下，低代码平台的生成物往往带来额外的授权与可控性问题，交付时会变成隐患。

## 技术

### 6. 为什么不做微服务？

因为交付对象决定形态。

客户现场通常是一到两台服务器，运维由客户或本地集成商承担。微服务引入的注册、网关、链路追踪、分布式事务，在这类场景里是纯成本，收益接近于零。

真正需要独立的只有**现场边缘节点**——部署位置不同、升级节奏不同、协议各异，拆出去是合理的。

### 7. 增加一个行业，需要改代码吗？

设计目标是**不需要**。

内核只认识对象、义务、证据、责任，不认识"电梯""气瓶""危废"。新增行业扩充的是知识与模板，不是系统本身。

我们把这件事当成架构的唯一验收标准：如果新增行业仍然要改内核，说明设计没兑现，后面也不具备规模化能力。

### 8. "不可篡改"具体怎么实现？能证明到什么程度？

三层结构：**只追加的记录通道** + **前后勾连的链式校验** + **与业务数据物理分离的每日锚点**。

**能证明的**：记录一旦产生，任何修改都会破坏校验；导出档案自带校验信息，监管可独立核对文件是否被替换过。
**不能证明的**：如果服务器与数据库的最高权限被同一人恶意掌握，纯软件方案存在边界。高要求场景需要引入第三方存证或时间戳服务——我们会如实说明，而不是含糊带过。

把边界讲清楚，比承诺"绝对不可篡改"更有价值。

### 9. 法规变了怎么办？改模板会不会弄乱历史数据？

不会。义务与检查口径带版本与生效期：新规生效后按新口径执行，历史记录仍按当时口径还原，两者互不干扰。

这正是"版本化"的意义——监管翻旧账时问的是"当时你依据的是哪一版"，而不是"你现在怎么规定的"。

### 10. 支持国产化环境吗？

支持国产操作系统、国产数据库与国产芯片平台的组合。

这是设计约束而不是事后适配：从第一天起就规避数据库特有语法与存储过程，否则后期迁移必然反复。

具体组合的兼容性以项目现场验证为准——不同版本之间确实存在差异，这部分会写入实施评估，不会拍胸脯保证。

### 11. 技术栈会不会绑死在一家供应商身上？

不会。技术体系是主流的 Java 与 Vue 生态，人才供给充分，集成商接手成本低；内核部分与具体框架解耦，领域规则不依赖框架特性。

我们刻意保留了这条退路：将来如果框架层需要更换，代价是可控的，而不是推倒重来。

## 部署与合规

### 12. 能离线部署吗？断网能用吗？

能，而且离线是底线而不是选项。安装包自带运行时、字体、文档转换组件与全部依赖，客户没有外网也能装完、能跑、能导出。

断网期间：现场记录本地留存，恢复后按序回传，不重不漏。涉及安全联锁的判定在现场侧执行，断网仍然生效。

### 13. 部署需要什么配置？

单机版一台常规服务器即可满足中小规模使用。政务云、集团多厂区或高并发场景按实际规模另算。

部署形态详见 [技术白皮书 第八节](./architecture.md#八部署形态)。

### 14. 数据存在哪里？监管认不认？

私有化部署时数据完全在客户侧，我们不接触、不托管；SaaS 模式下按租户隔离，由我们运维。

监管是否认可取决于对方流程与当地要求，这一点我们不做承诺。我们能保证的是：材料本身完整、可核验、格式符合常见报送要求，必要时可导出纸质档案。

### 15. 等保三级能过吗？

我们把软件侧该做的都做到位：七项安全要求逐条对表，配置基线、测评材料、国密改造支持随包交付，并配合整改与复测。

但测评结果取决于机房、网络、管理制度与运维流程的整体条件，软件不能单方面决定。任何声称"包过"的说法，建议谨慎对待。

### 16. 能对接上级监管平台吗？

具备完整对接能力，但**接口开放程度不由我们决定**。

做法是三层可配置：字段映射、报文模板、协议驱动；再加报文留痕与重放、对接自检工具。若对方接口确实拿不到，用辅助填报兜底——生成符合格式的文件由企业上传。

真实项目里这通常是最耗时的部分，会单独评估工作量，不会被写成一句轻飘飘的承诺。

## 合作

### 17. 二次开发难不难？

技术体系是主流的 Java 与 Vue，国内开发者普遍熟悉，招人与接手都不难。

更重要的是边界清晰：配置与模板改动不需要碰代码；行业特殊规则在受控的扩展点内实现；内核部分不建议修改——改了会导致历史记录无法自证，问题会延后暴露。

### 18. 源码授权是什么形式？

交付内核与行业能力源码，加部署文档与升级通道。授权范围按项目约定，通常区分自用、对外交付、再分发（白标）。

不包含：硬件、视频算法、第三方平台的商务关系。

### 19. 能不能换成我们自己的品牌？

可以（白标）。界面、Logo、域名、登录页、导出文件页脚都可替换，授权体系可独立签发。

需要注意许可证合规：底座部分为宽松许可，可商用可再分发，但需保留版权与许可证声明。合同里如实写明"基于开源底座二次开发"即可，既专业也没有风险。

### 20. 有没有演示环境或试用？

官网与演示环境在建设中，上线后会在本仓库公告。

在此之前，可以通过微信沟通后安排线上演示，或提供脱敏的界面说明与导出样例。暂不提供公开的在线试用账号——合规类系统数据敏感度高，公开试用的风险大于收益。
