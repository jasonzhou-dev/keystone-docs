# 常见问题

> 面向选型、尽调与实施准备的 20 个问题。
> 架构细节见 [architecture.md](./architecture.md)，产品概览见 [README](../README.md)。

**回答原则**：能做到的说能做到，做不到的说做不到，需要前提的说清前提。B 端软件最贵的成本是"买回来才发现不是那样"。

## A. 产品定位

### 1. 磐基是什么？

面向**法规强制型场景**的合规留痕中台：把法规条款翻译成可执行的周期性义务，用任务与现场取证把履行过程留成证据，再用不可篡改台账与导出档案证明"做过、没改过、谁负责"。

适用场景：特种设备、电梯维保、气瓶充装、排污许可与危废、食品、消防、职业健康等有明确法规义务、检查时会被要求"拿出来看看"的领域。

### 2. 和巡检 App / 打卡工具有什么区别？

| 监管会问 | 打卡工具 | 磐基 |
| --- | --- | --- |
| 对照的是哪一版清单？ | 只有当前版本 | 任务已固化模板版本，可复现 |
| 记录事后改过吗？ | 数据库可直接改 | 只追加 + 哈希链 + 每日锚点 |
| 谁负责、谁漏了？ | 没有责任主体 | 责任矩阵，带生效期与兼岗校验 |

概括：打卡工具证明"有人去过"，合规系统证明"履职了"。**没有版本化、没有哈希台账、没有责任矩阵的，就是打卡工具。**

### 3. 能不能只买一个行业包？

可以。行业包按需安装，交付包里只打你需要的模块。用不到的功能不占部署成本，也不占运维注意力。

### 4. 一套系统能不能同时管特种设备、环保、食品？

能，而且这正是它存在的理由之一。这些领域的内核是同一个（义务、日历、模板、取证、台账、闭环、报送、责任矩阵），差别在模板与报表。多领域共用一个底座的好处是：一个安全部门可以在一套系统里看到全部履职情况，而不是维护三套账号体系。

## B. 技术与数据

### 5. 为什么不做微服务？

因为交付对象是小团队和集成商。微服务带来的注册中心、网关、链路追踪、分布式事务，在"一个客户一台服务器"的场景里是纯成本。

实测判断是：微服务让交付成本约 ×3，而对这类业务的可用性、扩展性收益接近于零。真正需要拆出去的只有**边缘采集网关**——它部署在现场、独立升级、协议各异，拆出去是合理的。

### 6. 扩展性怎么保证？加一个行业要改代码吗？

设计目标是**不改**。判据只有一条：新增第 11 个行业包，改动内核代码行数是否为 0。

做法是四层：配置层（周期、检查项、字段、字典、审批链）、模板包层（检查项 JSON、报表模板、权限码）、接口实现层（检查规则、报表渲染、平台适配、设备驱动，控制在 500 行内）、内核层（禁止改）。

内核不认识"电梯""气瓶""危废"，只认识对象类型与模板。

### 7. "不可篡改"具体怎么实现？能证明吗？

三层，不做过度设计：

1. **只追加表**：应用侧没有 UPDATE / DELETE 权限，配合数据库审计
2. **哈希链**：每行哈希由上一条哈希 + 规范化内容 + 服务端时间计算得出，改一行则后续全部对不上
3. **每日存证锚**：把当天链头写入独立锚表（另一个库或另一个账号），大客户可选接时间戳服务或司法链

**能证明的部分**：导出档案里带模板版本、记录哈希、锚点编号，监管可用附带的校验工具自行验证文件未被替换。
**不能证明的部分**：如果数据库管理员与服务器管理员是同一个人且恶意配合，任何纯软件方案都有极限——这也是为什么高要求场景要接第三方存证。我们如实说明边界。

### 8. 法规变了怎么办？改了模板会不会把历史数据弄乱？

不会。义务、检查项模板、报表模板都带**版本与生效期**。新规生效后新建任务用新版本，历史任务仍固化了当时的版本号，渲染与导出按当时版本复现。

这正是"版本化"存在的意义：监管翻旧账时问的是"当时你对照的是哪一版"。

### 9. 支持信创吗？

支持麒麟 / 统信 + 达梦 / Kingbase + 鲲鹏 / 飞腾组合。前提是代码里禁用数据库特有语法与存储过程——这是设计约束，不是事后适配。

需要说明：具体信创组合的实际兼容性以项目现场验证为准，不同版本组合会有差异，这部分会写入实施评估。

## C. 部署与合规

### 10. 能离线部署吗？断网能用吗？

能，而且离线是硬要求不是选项。安装包内自带依赖、字体、文档转换组件与运行时，客户没有外网也能装完、能跑、能导出。

断网期间：取证数据本地排队，恢复后按序补传，幂等键保证不重不漏。关键联锁逻辑（例如"不扫码不开阀"）跑在边缘网关上，断网仍然生效。

### 11. 部署需要什么配置？

单机版 4C8G 一台起步即可满足中小规模使用。政务云或集团多厂区按并发与数据量另算。详细形态见 [architecture.md 第七节](./architecture.md#七部署形态矩阵)。

### 12. 数据存在哪里？监管认不认？

私有化部署时数据在客户自己的服务器上，我们不接触、不托管。SaaS 模式下数据在我们运维的环境，按租户隔离。

监管是否认可取决于对方流程与当地要求，我们不做承诺。我们能保证的是：材料本身可验证、格式符合常见报送要求、必要时可导出纸质档案。

### 13. 等保三级能过吗？

我们能提供测评所需的技术材料与配置基线（身份鉴别、访问控制、安全审计、入侵防范、数据完整性、备份恢复、个人信息保护逐条对表），也支持国密改造与密评配合。

但**"保证过等保"这种承诺我们不做**：测评结果取决于机房、网络、管理制度、运维流程等整体条件，不是软件单方面能决定的。任何声称"包过"的供应商，建议你谨慎。

### 14. 能对接省里的监管平台吗？

能对接，但**不承诺一次成功**。

现实情况是多数上级平台接口不公开、文档滞后、联调窗口有限。我们的做法是：可插拔适配器 + 界面可配的字段映射 + 可改的报文模板（JSON / XML / WebService / 表单），配合"辅助填报"兜底——生成符合平台格式的文件，由企业自行上传。

真实项目里这通常是最耗时的一块，会单独评估工作量，不写成"必须成功"的刚性条款。

## D. 交付与合作

### 15. 二次开发难不难？没接触过这套底座能改吗？

技术栈是 Spring Boot 3 + Vue 3 + MyBatis-Plus，国内主流组合。会用若依系底座的开发者基本能直接上手，招人也容易。

二次开发的边界是清晰的：配置和模板改动不需要碰代码；特殊规则实现接口；不建议改内核表结构与哈希逻辑（改了历史台账就无法校验，客户自己会踩坑）。

### 16. 源码授权是什么形式？

交付内核与行业包源码 + 部署文档 + 升级通道。授权范围按项目约定，通常区分：自用、对外交付、再分发（OEM）。

不包含：硬件、视频算法、第三方平台接口的商务关系。

### 17. 能不能换成我们自己的品牌？

可以（OEM 白标）。界面品牌、Logo、域名、登录页、导出文件页脚都可替换，授权体系可独立签发。

需要注意：底座为 MIT 许可，可商用可再分发，但需保留版权与许可证声明；内核与行业包为自有版权，按授权档位使用。合同里如实写明"基于 MIT 开源底座二次开发"即可，不必也不应宣称"完全自研"。

### 18. 有没有演示环境或试用？

目前官网与演示环境在建设中，上线后会在本仓库公告。

在此之前，如果需要评估：可通过微信沟通后安排线上演示，或提供脱敏的界面说明与导出样例。暂不提供公开的在线试用账号——合规类系统的数据敏感度高，公开试用环境的风险大于收益。

### 19. 移动端支持什么？

微信小程序、H5、App 三端，同一套代码。离线能力分三档：轻离线（本地队列 + 重传）、中离线（本地 SQLite 按序上送）、重离线（整厂内网走原生壳）。

如果现场是车间、地下室、井道这类无信号环境，建议选重离线方案，不要指望小程序覆盖。
