## 为什么现在必须做

监管的重心正在从**结果**转向**过程**。

- 过去查"有没有做"，现在查"怎么做的、谁做的、能不能证明没改过"
- 过去看纸质台账，现在看数据一致性与可追溯性
- 过去责任落在单位，现在要落到岗位与个人

这三件事叠加，意味着"事后补台账"的空间正在消失。留痕从一项行政工作，变成了需要系统承载的**证据工程**。

## 它解决什么问题

法规要求"日管控、周排查、月调度"，要求"无纸化维保""危废五即"，要求检查时**拿得出来**。
但实际情况通常是：

| 现实 | 后果 |
| --- | --- |
| 台账写在纸上、照片存在个人手机里 | 检查当天翻不出来 |
| 记录可以事后补、可以改 | 一旦被质疑真实性，无法自证 |
| 整改靠口头催 | 隐患不闭环，复查没依据 |
| 每个行业一套系统 | 换一个行业，重做一遍 |

磐基的做法是把**证据链**做成底座，行业差异只做模板：

```
法规条款 → 可执行义务 → 周期任务 → 现场取证 → 可信台账 → 履职档案
```

这条链路看着简单，难的是每一环都要经得起追问：**依据是哪一版？谁做的？时间可信吗？后来改过吗？**

## 能力全景

八个能力域，构成一套完整的履职闭环。行业差异体现在模板与报表，不在内核。

| 能力域 | 解决什么 |
| --- | --- |
| **合规对象治理** | 把单位、场所、设备、装置统一成可管理、可追溯的对象体系 |
| **义务与标准库** | 将法规条款转译为可执行、可版本化的义务与检查口径 |
| **合规日历** | 周期任务自动生成、按岗派发、逾期升级，不依赖人记 |
| **现场取证** | 一次采集即形成可采信的第一手证据，防代填、防事后补 |
| **可信台账** | 只追加、可校验的履职记录，具备自证能力 |
| **隐患闭环** | 从发现、整改、复查到销号的全过程追踪与责任归属 |
| **报送与档案** | 对外满足监管报送，对内一键生成履职档案 |
| **责任矩阵** | 岗位与职责的映射关系，支持兼岗校验与生效期管理 |

## 设计理念

四条原则，决定了这套系统长什么样。

**一、证据优先**

先想"怎么证明"，再想"怎么做"。功能设计的第一问不是"能不能填"，而是"填了以后，三个月后还站得住吗"。

**二、版本可溯**

法规会变、清单会变、口径会变。系统的责任是让任何一个历史时点都能被还原到**当时**的依据，而不是用今天的标准去解释昨天的记录。

**三、离线自治**

现场优先。网络是增强项，不是前提条件。断网、弱网、内网隔离，都不应该让记录丢失或让管控失效。

**四、边界清晰**

内核稳定，行业可变，定制有界。三者边界一旦模糊，产品就会退化成一个个项目。

## 架构分层

```
体验层    管理端 · 移动端 · 监管视图 · 开放接口
   │
行业层    行业知识与模板（可裁剪、可扩展、可替换）
   │
内核层    合规证据链（八大能力域）
   │
平台层    组织 · 权限 · 流程 · 文件 · 审计 · 授权
   │
集成层    监管平台对接 · 设备接入 · 第三方服务
   │
数据层    关系数据 · 缓存 · 对象存储

    ▲                                  ▲
    │                                  │
边缘节点（现场自治 / 断网续传）      上级监管平台 / 行业平台
```

三个设计取舍，值得说明：

**内核与行业彻底分离。** 内核不认识"电梯""气瓶""危废"，只认识对象、义务、证据与责任。因此新增一个行业，扩充的是知识与模板，而不是重写系统。

**现场与中心解耦。** 涉及安全联锁的判定放在现场侧执行，不依赖云端可用性。这类逻辑一旦上网才能生效，出事就是大事。

**对接做成能力而非承诺。** 上级平台接口的开放程度不由我们决定，因此对接被设计成可配置、可替换、可兜底的能力，而不是一句写进合同的保证。

## 与巡检工具的区别

市面上大量"合规系统"其实是巡检打卡工具。区别不在于功能多少，而在于**能不能回答监管的三个问题**：

| 监管会问 | 打卡工具 | 合规系统 |
| --- | --- | --- |
| 这次检查，你对照的是哪一版清单？ | 只有当前版本 | 记录与当时的依据绑定，可复现 |
| 这条记录事后改过吗？ | 数据库里能直接改 | 只追加 + 链式校验 + 独立锚点 |
| 谁该负责、谁漏了？ | 没有责任主体 | 责任矩阵，到岗到人 |

一句话：**没有版本化、没有可信台账、没有责任矩阵的，就只是打卡工具。**

## 合作方式

本仓库不放源码。系统按授权交付：

| 方式 | 适合谁 | 交付什么 |
| --- | --- | --- |
| **私有化交付** | 使用单位、园区、集团 | 部署 + 所需行业能力 + 一年运维 |
| **源码授权** | 集成商、有自研能力的集团 | 内核与行业能力源码 + 部署文档 + 升级通道 |
| **OEM 白标** | 想做自己产品的集成商 | 换品牌、换界面、独立授权体系 |
| **SaaS 订阅** | 小微企业 | 按年订阅，我们运维 |

具体报价按 **规模、行业范围、部署形态、对接复杂度** 四项核定——场景差异太大，统一报价必然是错的。

源码授权的边界：

- **可改**：配置、模板、界面品牌、扩展实现
- **不建议改**：内核的数据组织方式与校验逻辑（改了会导致历史记录无法自证，问题会延后暴露）
- **升级通道**：定制与内核分离，升级不需要重新交付定制部分
- **不含**：硬件、视频算法、第三方平台的商务关系

## 适用场景

- 有明确法规义务、检查时会被要求"拿出来看看"的使用单位
- 集团 / 园区，多个厂区需要统一留痕口径
- 需要离线部署、国产化环境或等保测评要求的项目
- 想承接合规类项目、但不愿从零构建底座的集成商

如果你只需要一个轻量的打卡记录工具，市面上有更简单、更便宜的选择——那类需求用不上这套东西。

## 常见问题

完整问答见 [docs/faq.md](./docs/faq.md)，这里放最常被问的六个：

**Q：和巡检 App 到底差在哪？**
巡检 App 记录"我去了、我拍了"；合规系统记录"依据是哪一版、什么时间、由谁、做了什么、事后有没有被动过"。前者证明有人去过，后者证明履职。

**Q：能不能只上一个行业方向？**
可以。行业能力按需启用，交付包里只包含你实际使用的内容。

**Q：断网能用吗？**
能。现场记录本地留存、恢复后按序回传；涉及安全联锁的判定在现场侧执行，断网仍然生效。

**Q：数据存在哪里，监管认不认？**
私有化部署时数据完全在客户侧，我们不接触。导出档案自带校验信息，监管可据此验证文件完整性。

**Q：法规变了怎么办？**
义务与检查口径带版本与生效期。新规生效后按新口径执行，历史记录仍按当时口径还原，两者互不干扰。

**Q：能对接上级监管平台吗？**
具备完整对接能力，但接口开放程度取决于对方。我们的做法是可配置的适配 + 辅助填报兜底，具体工作量在项目中评估。
