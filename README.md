## 它解决什么问题

法规要求"日管控、周排查、月调度"，要求"无纸化维保""危废五即"，要求检查时**拿得出来**。
但实际情况通常是：

| 现实 | 后果 |
| --- | --- |
| 台账写在纸上、照片存在个人手机里 | 检查当天翻不出来 |
| 记录可以事后补、可以改 | 一旦被质疑真实性，无法自证 |
| 整改靠口头催 | 隐患不闭环，复查没依据 |
| 每个行业一套系统 | 换一个行业，重做一遍 |

磐基的做法是把**证据链**做成底座，行业差异只做模板：

```
法规条款 → 可执行义务 → 定时任务 → 现场取证（照片/签名/GPS/时间戳）
        → 只追加台账（哈希链）→ 每日存证锚 → 检查时一键导出履职档案
```

## 与巡检 App 的区别

市面上大量"合规系统"其实是巡检打卡工具。区别不在于功能多少，而在于**能不能回答监管的三个问题**：

| 监管会问 | 打卡工具 | 合规系统 |
| --- | --- | --- |
| 这次检查，你对照的是哪一版清单？ | 只有当前版本 | 任务固化了模板版本号，可复现 |
| 这条记录事后改过吗？ | 数据库里能直接改 | 只追加 + 哈希链 + 每日锚点 |
| 谁该负责、谁漏了？ | 没有责任主体 | 责任矩阵（主要负责人 / 安全总监 / 安全员 / 岗位） |

一句话：**没有版本化、没有哈希台账、没有责任矩阵的，就只是打卡工具。**

## 技术架构

```
接入层    PC 管理端 │ 移动端（小程序 / H5 / App）│ 监管端看板 │ 开放 API
   │
行业包层  特种设备 │ 电梯 │ 气瓶 │ 环保 │ 食品 │ …        ← 只放模板、报表、权限码
   │
内核层    义务库 │ 合规日历 │ 检查模板 │ 现场取证 │ 不可篡改台账 │ 整改闭环 │ 报送导出 │ 责任矩阵
   │
平台层    认证 │ 多租户 │ 组织与数据权限 │ 字典 │ 工作流 │ 文件 │ 授权
   │
集成层    监管平台适配器 │ 硬件协议 │ 电子签章 │ 短信 │ OCR
   │
数据层    MySQL / PostgreSQL（信创：达梦 / Kingbase）│ Redis │ 对象存储

      ▲                                              ▲
      │                                              │
  边缘采集网关（工厂内网 / 断网续传）          监管平台 / 省固废 / 96333 / 气瓶追溯
```

五个关键决策，每个都有明确的取舍：

| 决策 | 选择 | 为什么不用另一个 |
| --- | --- | --- |
| 服务形态 | **模块化单体**（Maven 多模块） | 微服务交付成本 ×3，小团队和集成商装不起来；唯一拆出去的进程是边缘网关 |
| 底座 | Spring Boot 3 + Vue 3 | 集成商和开发者市场最熟，招人与接手成本最低 |
| 移动端 | uni-app（Vue 3） | 客户要微信小程序，原生和 Flutter 给不了；一套代码出小程序 / H5 / App |
| 定制边界 | **三层扩展，内核禁改** | 不为每个客户 fork 代码，否则第 20 个客户就崩了 |
| 对接 | 可插拔适配器 + 辅助填报兜底 | 省平台接口大多不公开，不能让它阻塞交付 |

## 证据链内核：八张核心表

这是整个产品真正的技术资产。剥掉行业外壳后，只剩这些：

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `ce_object` | 合规对象（单位 / 场所 / 设备 / 管线 / 车辆 / 罐） | 类型、编码、父级、扩展属性 |
| `ce_obligation` | 义务库（法条 → 义务） | 来源文件、条款、周期、取证规则、**版本、生效期** |
| `ce_checklist_tpl` | 检查项模板 | 行业包、对象类型、检查项、**版本** |
| `ce_plan` | 周期计划 | 义务、周期规则、派单规则 |
| `ce_task` | 任务实例 | 计划、截止时间、责任人、**固化的模板版本** |
| `ce_evidence` | 取证 | 类型、文件、SHA-256、GPS、设备时间、服务端时间、签名 |
| `ce_ledger` | 台账（只追加） | 前序哈希、本行哈希、内容、锚点 |
| `ce_finding` / `ce_rectify` | 隐患 / 整改闭环 | 等级、期限、升级时点、复查人 |

外加两张支撑表：`ce_role_matrix`（责任矩阵，带生效期与一人多职校验）、`ce_submission`（报送批次 + 回执 + 报文摘要）。

### 为什么"版本化"是分界线

监管翻旧账时问的是：**2026 年 3 月那次日管控，你对照的是哪一版清单？**

所以任务实例必须固化模板版本号，渲染与导出都用当时那一版。这是普通巡检 App 做不到、也不愿意做的地方——**它决定了你做的是"合规"还是"打卡"**。

同理，法条每年变，义务和报表也要带生效期：旧记录按旧版本复现，新任务按新版本执行，中间不断档。

### 不可篡改：三层，不过度设计

```
第 1 层  只追加表（应用侧无 UPDATE / DELETE 权限）+ 数据库审计
第 2 层  哈希链：hash_i = SM3( prev_hash ‖ 规范化JSON(内容) ‖ 服务端时间 )
第 3 层  存证锚：每日把链头写入独立锚表（另一个库 / 另一个账号），
         大客户可选对接时间戳服务或司法链
```

三个决定成败的工程细节：

1. **双时间**：设备时钟与服务端接收时间都存，并计算时差；判定以服务端为准
2. **原图存证**：照片与视频存对象存储，SHA-256 入库，导出时附校验工具，监管可自行验证未被替换
3. **可复现导出**：PDF 页脚打印"模板版本 + 记录哈希 + 锚点编号"，形成闭环

> 国密（SM2 / SM3 / SM4）做成可切换的加密提供者，默认国际算法，等保 / 密评客户切国密。

## 扩展模型：第 N 个行业包只写模板

这是判断这套架构成不成立的**唯一标准**：

> **新增第 11 个行业包，改动内核代码行数是否为 0？**

四层，定制只允许发生在第三层：

```
第 1 层  配置层（大部分定制都在这）
         周期规则、检查项、字段、字典、角色名、审批链、报表映射

第 2 层  模板包层（行业差异都在这）
         检查项 JSON、Word/Excel 报表模板、菜单权限码、初始化数据

第 3 层  接口实现层（客户特殊要求，控制在 500 行内）
         检查规则 / 报表渲染 / 平台适配 / 设备驱动 / 导出器

第 4 层  改内核 —— 禁止
```

一个行业包 = 一个目录 + 四样东西：

```
keystone-pack-xxx/
├─ module.json        菜单、路由、权限码、依赖的内核能力版本
├─ templates/*.json   检查项模板（按对象类型，带版本）
├─ reports/*.docx     监管报送与履职档案模板
├─ sql/               初始化数据（字典、模板、权限）
└─ src/main/java      仅领域校验，不得操作内核之外的表
```

**内核不认识"电梯""气瓶""危废"，只认识对象类型和模板。** 这条守住了，新行业包就只是写模板。

工程上还有两个硬约束：内核仓库独立、行业包独立、客户定制独立目录；持续集成检查 `customers/` 与 `packs/` 不得修改内核内部类，只能实现接口。每个客户的交付物 = 内核版本 + 行业包版本 + 定制层提交，可复现构建。

## 部署形态

| 形态 | 适用 | 交付方式 |
| --- | --- | --- |
| **单机版** | 单一企业、小集成商 | 4C8G 一台，Windows 一键离线包或容器编排 |
| **私有化版** | 集团、园区 | 离线镜像 + 增量升级包 |
| **政务云 / 等保三级** | 政府、园区 | 双机或容器化 + 国密 + 审计，配套测评材料 |
| **SaaS 多租户** | 小微企业 | 共享库 + 租户隔离，我们运维 |
| **边缘采集网关** | 工厂现场 | 独立进程，单独安装、单独授权 |

离线是硬要求，不是选项：**依赖、字体、文档转换、运行时全部打进安装包，客户没有外网也能装完、能跑、能导出。** 断网 24 小时后恢复，取证数据零丢失、零重复。

边界情况：

| 项 | 做法 |
| --- | --- |
| 信创 | 麒麟 / 统信 + 达梦 / Kingbase，代码里禁用数据库特有语法与存储过程 |
| 等保 2.0 三级 | 身份鉴别、访问控制、安全审计、入侵防范、数据完整性、备份恢复、个人信息保护逐条对表 |
| 商用密码应用 | 国密传输 + 存储加密 + 签名验签，测评材料随包交付 |
| 视频 | 不自建流媒体，接海康 / 大华 / GB28181 平台 |
| 性能口径 | 单机满足园区并发 ≥300、在线 ≥1000；瓶颈在图片上传与报表生成，用异步队列 |

## 合作方式

本仓库不放源码。系统按授权交付：

| 方式 | 适合谁 | 交付什么 |
| --- | --- | --- |
| **私有化交付** | 使用单位、园区、集团 | 部署 + 所需行业包 + 一年运维 |
| **源码授权** | 集成商、有自研能力的集团 | 内核与行业包源码 + 部署文档 + 升级通道 |
| **OEM 白标** | 想做自己产品的集成商 | 换品牌、换界面、独立授权体系 |
| **SaaS 订阅** | 小微企业 | 按年订阅，我们运维 |

具体报价按 **规模、行业包数量、部署形态、对接工作量** 四项核定——场景差异太大，统一报价必然是错的。

关于源码授权，几个边界先说清楚：

- **可以改**：配置、模板、接口实现层、界面品牌
- **不建议改**：内核表结构与哈希逻辑（改了历史台账就无法校验，客户自己会踩坑）
- **升级通道**：定制层与内核分离，因此升级不需要重新交付你的定制代码
- **不含**：硬件、视频算法、第三方平台接口的商务关系

## 适合谁 / 不适合谁

说清楚不做什么，比列一堆功能更有用。

**适合**：

- 有明确法规义务、检查会被问到"拿出来看看"的使用单位
- 集团 / 园区，多个厂区要统一留痕口径
- 想接合规类项目、但不想从零写底座的集成商
- 需要离线部署、信创环境或等保测评的项目

**不适合**：

- 只想要一个便宜打卡工具，不需要版本化和证据链
- 要求"保证过检查""保证过等保"——这类承诺我们不做，也建议你别信
- 要求把省平台对接写进合同刚性条款——接口大多不公开，能承诺的是"提供对接能力 + 辅助填报"
- 需要自研视频 AI 算法——硬件厂商的战场，我们只做接入

## 常见问题

完整 20 条见 [docs/faq.md](./docs/faq.md)，这里放最常被问的六个：

**Q：和巡检 App 到底差在哪？**
差在监管认可度。巡检 App 记录"我去了、我拍了"；合规系统记录"我依据哪一版清单、在什么时间、由谁、做了什么、事后有没有被改过"。前者能证明有人去过，后者能证明履职。

**Q：能不能只买一个行业包？**
可以。行业包按需安装，交付包里只打你需要的模块，不为用不到的功能付部署和维护成本。

**Q：断网能用吗？**
能。取证数据本地排队，恢复后按序补传；关键联锁逻辑（例如不扫码不开阀）跑在边缘网关上，断网也生效。

**Q：数据存在哪里，监管认不认？**
私有化部署时数据在你自己的服务器上，我们不接触。导出的档案带模板版本、记录哈希与锚点编号，监管可自行校验——认不认取决于对方流程，但材料本身是可验证的。

**Q：法规变了怎么办？**
义务与模板带版本和生效期。新规生效后新建任务用新版本，历史记录仍按旧版本复现，不会因为改模板把过去的数据弄乱。

**Q：能对接省里的平台吗？**
能对接，但**不承诺一次成功**：多数省平台接口不公开，我们的做法是适配器 + 字段映射 + 报文模板可配，配合"辅助填报"兜底。真实项目中这通常是最耗时的一块，会单独评估工作量。
